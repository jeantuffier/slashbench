Slashbench

Does Rust actually cost less to run than JVM/JS backends? A reproducible benchmark for "Rust will slash your backend costs" — JavaZone 2026.

Methodology

Six stacks in three families — Rust (Rocket, Actix-web), JVM (Java + Spring Boot, Kotlin + Spring Boot), JS (Node + Hono, Bun + Hono) — implement the identical CRUD API against the identical Postgres schema, with a matched raw-driver DB tier (no ORM) so runtime overhead isn't confounded with ORM overhead. Each family holds one variable constant and varies the other, producing two "does this even matter?" control results before the cross-family comparison.

For each stack: a burst sweep steps memory down at a fixed target load until the SLA breaks, and the last passing rung is soak-confirmed by surviving sustained load for real (a footprint that only survives a few seconds isn't necessarily stable — see the per-stack detail below for cases where it wasn't). The monthly cost estimate uses GCP Cloud Run's instance-based (always-on) pricing against each stack's soak-confirmed footprint.

A second finding: recovery from a shared disruption under sustained load

During the 10-minute sustained-load soak, every stack occasionally experiences the same brief, external-looking disruption — even Rocket and Actix-web show one anomalous slow sample each. What differs is recovery: Rocket and Actix-web absorb it near-instantly (one slow sample, then straight back to baseline), keeping their whole-run p99 comfortably under the SLA. Three stacks — Java + Spring Boot, Kotlin + Spring Boot, and Node + Hono — do not: the same brief event turns into an extended, multi-hundred-millisecond-to-multi-second tail severe enough to fail the SLA, consistently, across every independent attempt tested (3-6 attempts per stack, all failing). More memory doesn't fix it — Java + Spring Boot still failed identically at 3x its normal allocation.

Bun + Hono is a genuine borderline case, not grouped with either side: across 3 independent attempts, it passed once and failed twice. It sits closer to the Rust stacks' fast-recovery behavior than to the other three's consistent failure, without being as reliable as Rocket/Actix-web. Postgres checkpoint I/O, container file-descriptor limits, GC heap pressure, and load-generator CPU contention were each tested directly and ruled out as the cause of the *severity difference* between stacks — the disruption itself is shared and external; only the recovery gap is stack-dependent. Full investigation: CLAUDE.md's Aug 20 entries.

A GCP-specific gotcha: the always-on 1-vCPU floor

Cloud Run's instance-based (always-on) billing tier has a hard minimum of 1 full vCPU — fractional CPU is only available under its separate request-based tier. Checked this against AWS Fargate, Azure Container Apps, and Scaleway Containers too: none of them have this floor — all three support fractional CPU (0.25, 0.25, and 0.07 vCPU minimums respectively) as their only billing mode, no GCP-style split between a floor-bound "always-on" tier and a fractional "request-based" one. So this is a real platform quirk specific to GCP's instance-based tier, not a universal cloud-economics fact. Since this benchmark holds CPU fixed at 1 vCPU throughout (to isolate memory as the tested variable), that same vCPU is also the real floor if you deploy this way on Cloud Run specifically — not a test artifact. The chart below splits it out: the fixed floor is identical for every stack (~$88/month); the memory-driven cost — the thing that actually varies — is the thin sliver on top, $0.10-$2/month in this dataset. The footprint chart above is the more honest headline; the fractional-CPU price comparison further down is the fairer cross-provider one.

A related finding: memory floor vs. actual usage

Prompted by a direct question the numbers above raise: why do the two JS runtimes survive on a smaller memory ceiling than either Rust stack, when Rust has no garbage collector and should need less memory, not more? Answering it needed a separate, targeted check outside the main sweep/soak pipeline — running the identical sustained load (800 req/s, no CPU cap change) against rocket, node-hono, and bun-hono at a shared, deliberately generous 512 MiB ceiling (far above any of their sweep floors, so none of them are under memory pressure), sampling each container's real cgroup memory (memory.current) every 5 seconds for 150 seconds.

StackSteady-state RSS (512 MiB headroom, 800 req/s)Sweep floor (minimum survivable)
rocket~36 MiB (flat)128 MiB
bun-hono~104–112 MiB48 MiB
node-hono~145–169 MiB96 MiB

One-off manual diagnostic (single load level, single run per stack), not part of the automated sweep/capacity/price-sweep pipeline — illustrative of the mechanism below, not a precise, repeated measurement.

Under identical, pressure-free conditions, Rust genuinely does use far less memory — 3–4x less than either JS runtime here. That's the opposite of what the sweep floor alone suggests, and it points at what the floor number actually measures: not baseline efficiency, but elasticity under pressure. V8 (Node) and JavaScriptCore (Bun) manage an adaptive heap — given spare headroom, they let it grow, since a bigger heap means fewer, cheaper GC cycles; squeezed into a tight ceiling (exactly what sweep's descending memory ladder does), the same collector compacts far more aggressively and reaches a much smaller real working set. Rust's allocator (plain glibc malloc here — confirmed via ldd, no jemalloc/mimalloc) does the opposite: it stays close to the live set regardless of how much cgroup headroom is available, which is exactly why it's flat at ~36 MiB whether given 512 MiB or far less — but that also means there's no adaptive "fat" to compress away when squeezed. Whatever headroom it genuinely needs beyond that lean baseline (connection buffers, in-flight request state, momentary allocation spikes under concurrent load) has to fit as hard bytes, and that appears to hit a wall around 128 MiB.

A ruled-out alternative worth naming: the first hypothesis was that Rust's async runtime (Tokio) was over-provisioning worker threads because Docker's CPU quota doesn't hide the host's real core count from /proc/cpuinfo — confirmed true (every stack sees all 4 host cores despite the 1.0 vCPU limit), but checking actual thread counts falsified it as the explanation: rocket (2 threads) and actix-web (3) both have fewer OS threads than node-hono (7) or bun-hono (6), the opposite of what that theory predicted.

Two independent things point the same direction: Scaleway's instance is ~18% cheaper at list price, and delivers genuinely more real hardware for that lower price — 4 independent modern cores instead of 2 older cores split via hyperthreading (hyperthreads share their physical core's execution units, cache, and memory bandwidth, so they don't deliver anywhere near 2 full cores' worth of throughput under concurrent load — exactly the kind of load a busy database serving many simultaneous connections produces). This is a snapshot comparison of one instance-type pairing at list price on one day, not a systematic survey — GCP offers non-hyperthreaded, compute-optimized families (e.g. c2/c3) that a fuller comparison would need to include, and cloud CPU platforms/pricing can change without notice. A reasonable, though not separately measured, implication: if the hardware gap holds under real production load, a workload needing N GCP instances could plausibly run on fewer Scaleway ones for the same throughput — which would compound the per-hour price gap into a larger total infrastructure-cost gap than the table above shows on its own.
