# Slashbench

Reproducible cloud-cost benchmark behind the JavaZone 2026 talk **"Rust will slash your backend costs"** (Oslo, Sept 2–3, 2026).

Full rendered plan (same content as below, nicer to read): https://claude.ai/code/artifact/a9063189-6028-4c7b-9684-40b0e1dd7ac8

## Why this project exists

Two blog posts inspired the talk (aismith.dev "rust-green-backend-slashes-cloud-bills" and worldwithouteng.com "i-saved-87-percent-on-compute-costs-by-switching-languages"). Neither survives scrutiny: the first has no methodology at all (invented scenarios, no frameworks named, no benchmark); the second generalizes an 87% saving from one IO-bound service migrating Rails→Actix-web, explicitly untested on CPU-bound workloads. This project replaces both with something reproducible that others can re-run and check.

**Hypothesis:** Rust backends use less memory than JVM/JS backends serving the same workload, and that difference translates into a measurably smaller cloud bill.

## Experimental design

Six stacks, three families. Each family holds one variable constant and varies the other, producing two "control" results before the headline cross-family comparison.

| Family | Stack | Constant | Varies | Tests |
|---|---|---|---|---|
| JVM | Java + Spring Boot | Framework (Spring Boot) | Source language | Java vs Kotlin on same runtime (expect: barely) |
| JVM | Kotlin + Spring Boot | | | |
| JS | Node.js + Hono | Framework (Hono, runs on both) | Runtime engine | V8/libuv vs JavaScriptCore/Bun (expect: measurable) |
| JS | Bun + Hono | | | |
| Rust | Rust + Rocket | Language (compiled) | Framework | Framework choice when compiled (expect: barely) |
| Rust | Rust + Actix-web | | | |

**Why Hono for both JS runtimes:** using Express for Node and Elysia for Bun would confound runtime with framework. Hono has first-class adapters for both (`@hono/node-server`, native Bun support), so runtime is the only variable that changes.

**Anticipate in Q&A:** "what about GraalVM native image / Quarkus / Micronaut?" — the JVM ecosystem's actual answer to memory bloat. Out of scope for the 11-day build; decide whether to name it as a caveat up front (stronger) or hold for Q&A.

## Benchmark application spec

Same functionality, schema, and seed data, implemented six times. Deliberately simple — this is a memory/runtime-overhead benchmark, not a framework-feature bakeoff.

| Endpoint | Behavior |
|---|---|
| `POST /items` | Validate, insert a row, return created item as JSON (write path + serialization) |
| `GET /items/:id` | Point read by primary key, JSON (read path + connection pool under concurrency) |
| `GET /items?page=&limit=` | Paginated list query, JSON array (query planning + larger payload serialization) |

Single shared Postgres instance, identical schema and seed script, reseeded between stacks.

**DB access tier — decided:** raw drivers only, no ORM, matched across all six so language/runtime overhead isn't confounded with ORM overhead:
- Java/Kotlin: `JdbcTemplate` / Spring Data JDBC (no Hibernate)
- Node/Bun: `postgres` (porsager/postgres.js) — same driver both runtimes
- Rust: `sqlx` — same crate under Rocket and Actix-web

Trade-off accepted: doesn't reflect a typical Hibernate-based Spring app in production — worth one framing sentence in the talk.

## Fairness & environment rules

- All six built from the same `docker-compose.yml` pattern, one profile per stack.
- Run **one stack at a time** against a freshly reseeded DB.
- Load generator (k6) runs on a **separate** machine from the service under test — otherwise k6's own CPU pollutes the container's measured stats, and loopback hides real latency.
- Fixed-spec cloud VMs, not a laptop — two `e2-standard-4` GCE VMs (one "target," one "load generator"), so anyone re-running this gets the same playing field.
- Randomize run order across repeats to avoid host-drift bias (thermal creep, disk cache state).

## Core measurement: minimum viable footprint

Cloud Run instance-based billing charges for CPU/memory **allocated** to a container for as long as it runs, not what it uses internally. The number that drives the bill is: **the smallest instance size each stack can be provisioned at while still meeting an SLA under the same load.**

Sweep procedure (automated by the CLI):

1. Dry-run **all six** stacks uncapped to find each one's max sustainable throughput. Set the shared target load at ~60% of the **weakest** stack's ceiling — Rocket will very likely be the fastest of the six, so it cannot be the anchor even though it's built first. This step happens once all six are running (~Aug 17), not right after Rocket alone.
2. SLA (placeholder, confirm after step 1): p99 latency < 200ms and error rate < 1%, sustained 5 min at target load.
3. Fix CPU generously (1 vCPU) — memory is the headline claim, not CPU. Step memory down (512→384→256→192→128→96→64 MiB…) via `docker run --memory` until the SLA breaks. Last passing value = that stack's minimum viable footprint.
4. At that minimum footprint, run one ~1 hour soak test — surfaces JVM GC pause growth or slow leaks, makes for a strong "memory over time" slide against Rust's flat line.

Each sweep step repeated **3×** minimum; report median with IQR, not a single sample.

## Load testing & metrics

- **k6**: one script hits all three endpoints in a realistic mix (e.g. 70% reads / 30% writes), reused unmodified across every stack.
- **docker stats / cgroup v2**: CPU% and RSS sampled every second per run.
- Captured per run: achieved RPS, p50/p95/p99 latency, error rate, mean & peak CPU%, mean & peak RSS, cold-start time, and (from the sweep) minimum viable memory footprint at the SLA.

## Cost model

GCP Cloud Run, instance-based tier (always-on, matches "backend service that must stay warm" rather than scale-to-zero):

| Unit | Price (beyond free tier) |
|---|---|
| per vCPU-second | $0.0000336 |
| per GiB-second | $0.0000035 |
| per million requests | $0.40 |

```
monthly_cost = (vCPU_allocated × 0.0000336 + GiB_allocated × 0.0000035) × seconds_per_month
             + (requests_per_month ÷ 1_000_000) × 0.40
```

**Verify before publishing** — cloud pricing changes. Keep these in a versioned `pricing.json` with a "last verified" date and a link to https://cloud.google.com/run/pricing, not hardcoded in the report generator.

## CLI tool architecture

One command runs everything end to end: `slashbench run --stack all --sweep --soak`. Written in Rust (fitting, given the subject).

```
CLI: slashbench run
  → reseed Postgres
  → start one stack's container at current memory ceiling
  → warm-up window
  → k6 load test from load-gen VM
  → sample docker stats (CPU/RSS, 1s interval)
  → SLA met? yes → step memory ceiling down, repeat
             no  → record minimum viable footprint for this stack
  → soak test at minimum footprint
  → next stack
  → aggregate results → cost model → report
```

Report output: raw JSON/CSV per run (so others can recompute with their own provider's pricing) plus a generated Markdown/HTML report with the footprint chart, the memory-over-time soak chart, and the methodology/limitations section inline.

## Known limitations to state up front in the report

- Single-machine measurement, not a distributed production topology.
- JVM steady-state throughput improves after JIT warm-up — the soak test's early window will look worse for Java/Kotlin than its later window. Report both windows, don't average them away.
- Six implementations by one person — skill/effort asymmetry across stacks is a real confound. Mitigated by using each ecosystem's standard idioms (not hand-tuned tricks) and by open-sourcing the code so others can flag an unfair implementation.
- Instance-based billing (always-on) is one Cloud Run billing mode, not the only one — request-based (scale-to-zero) billing tells a different, concurrency-dependent story. Named as a deliberate scope choice, not an oversight.
- This benchmark measures short-term resource efficiency under sustained load (minutes — the soak test runs 20 minutes per candidate), not long-term production stability (months). A stack's footprint here doesn't rule out different drift in real production over a much longer horizon — memory creep, GC tuning decay, dependency bloat — the kind of effect anecdotal reports (e.g. a Spring Boot vs Node.js cost comparison over 18 months) point at but can't rigorously isolate either. Named as a scope boundary, not a rebuttal of that concern.

## Data safety & backup

The code is the easy part — commit and push to GitHub daily and it's already redundant. The actual risk is the **sweep/soak dataset**, generated on disposable GCE VMs intended to be torn down right after the deadline.

- CLI orchestrator writes results incrementally (append-only JSON Lines per completed sweep step), not one buffered write at the end — a crashed VM mid-sweep then costs the last step, not the whole day's runs.
- Sync results out of the VM into the git repo **after each stack finishes** (Aug 22), not after all six.
- Before terminating the VMs on Aug 23, tag a GitHub release with the final raw dataset attached — the durable, timestamped copy the talk's numbers are built on.
- Repo is public from day one anyway, so no secrets-in-git concern beyond not hardcoding the GCE project ID / billing account into committed config.

Results append to `results/soak-{stack}.jsonl` — small time-series data, meant to be committed (unlike `sweep.jsonl`), since it's the direct input for the "memory over time" chart. Early-stops a stack's soak if a chunk shows ≥90% errors (container's dead — no point burning the rest of the run against it).
  - **First validation run found a genuine methodology gap, not just a code bug.** Ran actix-web at its sweep-declared minimum (8 MiB, found via a few 8-20s bursts) under 200 req/s sustained load: memory climbed 6.09 → 7.45 → 7.35 MiB across the first 30s, then the container died mid-chunk (12.1% errors at t=30s, confirmed fully dead at t=59s — "container is not running", 100% errors). The tool correctly detected this and stopped early rather than continuing against a dead container.
  - **Implication for the whole project, not just this one number:** the sweep's short-burst methodology (§4 steps 1-3) can be too optimistic — a footprint that survives a few seconds of load doesn't necessarily survive sustained operation. **A stack's minimum viable footprint should not be reported as final until it also survives a soak test at that footprint** — if the soak fails, the real answer is one rung higher on the sweep's memory ladder, re-soaked to confirm. None of the six sweep-summary.json numbers collected so far (§ prior entries) have been soak-confirmed yet; treat all of them as provisional candidates, not final answers, until this happens. This applies to the eventual GCE run too, not just today's local shakedown — worth deciding whether to automate the "bump and re-soak until stable" loop into the sweep itself, or keep it a manual follow-up step.

- **Aug 15, 2026 — soak redesigned as truly continuous, and integrated into sweep as an automatic confirmation loop.** Jean pushed back on two things and both were real gaps, not just preferences:
  - **Continuity**: the original soak chunked the duration into repeated short k6 processes (reusing the blocking `k6::run`), leaving small gaps between chunks where the load generator restarted. Replaced with `k6::spawn()`/`K6Handle` (non-blocking child process) — one uninterrupted k6 process for the entire soak duration. Memory and a lightweight canary request (`GET /items?page=1&limit=1`) are sampled on a separate timer instead, appended to `results/soak-{stack}.jsonl` as `{"kind":"sample",...}` rows; a `{"kind":"aggregate",...}` row is appended once at the end from k6's own whole-run summary. Two consecutive canary failures = the container's dead; `handle.kill()` stops k6 immediately rather than waiting out the rest of the duration. Trade-off made explicitly: this loses k6's fine-grained per-chunk latency breakdown (now one aggregate for the whole run) in exchange for genuinely continuous load — memory-over-time (the actual point of this test) stays fully time-resolved either way.
  - **Sweep integration**: `sweep` now soak-confirms automatically. After the burst ladder walk, it collects every burst-passing rung (not just the last), then tries soak-confirming starting from the smallest and bumping up to the next larger burst-passing rung each time a candidate fails soak, until one is confirmed or all burst-passing rungs are exhausted. `results/sweep-summary.json` now reports both `burst_minimum_mb` (raw short-burst result) and `soak_confirmed_mb` (the authoritative number, `null` if nothing tested held up). New flags: `--soak-total-duration` (default "2m", official runs need much longer), `--soak-sample-interval` (default "15s"), `--skip-soak-confirmation` to opt out for fast burst-only iteration. `lookup_minimum_viable_mb` (used by the standalone `soak` subcommand's default) now prefers `soak_confirmed_mb`, falling back to `burst_minimum_mb` with an explicit warning if a stack hasn't been soak-confirmed yet.
  - **Validation surfaced a real methodological subtlety, not just confirmed the code works.** Ran node-hono's continuous soak twice at its own sweep-declared 24MiB floor: the standalone test died at elapsed≈50-60s (memory ~23.1-23.4 MiB right before death); the sweep-integration test at the same footprint ran the full 70s and PASSED, memory sitting in the same ~23.3-23.5 MiB range throughout. Same footprint, same target load, genuinely different outcomes — 24MiB is a knife's-edge result for this stack, close enough to the ceiling that survival isn't deterministic run-to-run.
  - **Open question this raises**: a single soak PASS may not be strong enough evidence when the margin is this tight — the burst sweep already requires 3 repeats + median specifically to guard against single-run noise; soak-confirmation currently doesn't have an equivalent (it's one soak, pass or fail). Worth deciding whether to require N consecutive soak passes before confirming a candidate (mirroring the burst methodology's own rigor), which would multiply soak time by N, or accept single-run confirmation with this flakiness documented as a known limitation.

- **Aug 17, 2026 (later still) — found and fixed a real Rust/Hyper accept-backlog bug that was capping Rocket and Actix-web's throughput, the opposite direction of this benchmark's whole hypothesis.** The first real dry-run (with the new rigor) showed Rust stacks capping at 400 req/s while JVM/JS all reached 1600 — a 4x gap in the wrong direction.   - **Packet capture** (`tcpdump`) during a failure window: no premature FIN/RST from either side; the real signature was SYN retransmission with classic Linux exponential backoff (1s→2s→4s→8s) and **zero SYN-ACK response ever** — a silent drop, the standard kernel behavior when a listen backlog is full.
  - **Root cause confirmed two ways**: Hyper 0.14's `AddrIncoming::new()` calls `StdTcpListener::bind()` directly (checked actual source), and Rust's `std::net::TcpListener::bind()` hardcodes backlog=128 on Linux ([rust-lang/rust#55614](https://github.com/rust-lang/rust/issues/55614)) — confirmed empirically via `nsenter` into the live container's network namespace (bypassing a red herring: the host-level `docker-proxy` socket showed a generous 4096, but that's a separate forwarding layer, not Rocket's real listener). Verified the referenced GitHub fix ("trust the platform's SOMAXCONN") does **not** apply to current stable Rust (1.97.1) for plain `std::net::TcpListener` — built and ran an isolated minimal Rust binary (no Hyper/Rocket) that reproduced backlog=128 on this exact toolchain, so this isn't a stale-issue misunderstanding, it's the real current behavior.
  - **Rocket 0.5.1 has no way to fix this via its own API** — a `Listener` trait for injecting a custom pre-bound socket is real but explicitly scoped to "the next major release after v0.5" per Rocket's own announcement; not available in our locked 0.5.1.
  - **Fixed via `LD_PRELOAD` libc interception instead** (`services/{rocket,actix-web}/listen_override.c`): a ~20-line shared library intercepting `listen(2)` and forcing the backlog up to `somaxconn` (4096) regardless of what the application requests — zero changes to either Rust service's own code. Compiled as a Dockerfile build stage (`gcc:latest`), wired in via `LD_PRELOAD=/app/listen_override.so` in `docker-compose.yml`. Verified standalone first (isolated test binary: 128→4096), then confirmed on both real services (Rocket requests 128, Actix-web requests 1024 — matching its documented default — both forced to 4096) via the same `nsenter` technique.
  - **Also fixed while re-running: `dry_run.rs` didn't isolate per-stack start failures** the way `sweep.rs`/`capacity.rs` already do — a transient Docker DNS blip on Actix-web (`Temporary failure in name resolution`, unrelated to the backlog fix — the shim fired correctly on that same run) killed the entire 6-stack run and lost Rocket's already-good result. Fixed to match sweep's existing "a failure costs one stack, not the run" pattern.
  - **Real, fully clean 6-stack dry-run result after both fixes**: rocket now reaches **1600 req/s** cleanly (was 400 — a genuine 4x fix, now matching every JVM/JS stack), spring-java/spring-kotlin/node-hono/bun-hono all still 1600. **Actix-web is still stuck at exactly 400**, despite the identical shim confirmed active on it too (`nsenter` showed its backlog is genuinely 4096 now). This means Actix-web has a *different* remaining bottleneck the backlog fix didn't touch — unresolved, needs its own investigation. Weakest-stack/target-load calibration is therefore still anchored on Actix-web's 400 (target load 240 req/s), unchanged from before, even though Rocket's own number is now far more honest.
  - **VMs stopped again at end of session.** Same IDs/restart commands as the prior entry.

- **Aug 18, 2026 — Actix-web's separate bottleneck found and fixed: a real, documented actix-web keep-alive bug, unrelated to the backlog issue.** Resumed cleanly (VMs restarted, bridge re-verified with zero issues this time). Investigated with the same rigor as the Rocket bug, falsifying each hypothesis with direct evidence before moving to the next:
  - **Worker count**: raised from the default 4 to 64 — made it *worse* (introduced actual errors that weren't there before). Ruled out.
  - **DB pool exhaustion**: raised `max_connections` from 20 to 200 — zero effect on the stall. Also checked `pg_stat_activity` live during a failure window (25 samples across a full failing test) and saw **zero** Actix-web activity at any point — the stuck requests never reach Postgres as a query at all. Ruled out.
  - **On-demand connection creation / slow DNS**: added `min_connections(20)` to pre-warm the pool before load starts — zero effect. Ruled out.
  - **TCP-level data retransmission**: captured a live failure window with `tcpdump` + `tshark`'s retransmission analysis. First pass showed 31,911 "retransmissions" — almost entirely a capture artifact (same packet counted 2-3× across Docker's physical/bridge/veth interfaces when capturing on `-i any`, the same gotcha from the earlier FIN/SYN investigation). Redone on the single correct veth interface (found via `iflink`/`ifindex` matching from inside the container's netns): **1 real retransmission out of 59,173 packets.** Ruled out — no real network loss.
  - **Root cause isolated directly**: re-ran the Mode A/B connection-reuse test (from the Rocket investigation) specifically against Actix-web, which hadn't been done yet — `--no-connection-reuse` was completely clean (799.8/800 req/s achieved, p99=8.5ms, only 3 VUs needed), while default reuse still showed the ~22s stall on 2-4% of requests. This pinpointed connection reuse/keep-alive specifically, not admission or capacity.
  - **Confirmed via research, not just isolation**: actix-web's default keep-alive is 5 seconds, and there's a long-documented actix-web issue ([actix/actix-web#1759](https://github.com/actix/actix-web/issues/1759)) describing exactly this failure mode — a request sent on a reused connection right as the server closes it at the keep-alive boundary gets silently lost, and the client has to detect and recover, which is where the ~22s comes from (client-side retry/timeout recovery, not a network-level delay).
  - **Fixed**: `.keep_alive(Duration::from_secs(75))` on Actix-web's `HttpServer` builder — one line, no architecture changes. Verified twice for reproducibility at rate=800 (p99=8.99ms then p99=8.42ms, 0% errors both times, vs. consistent ~22.5s stalls before) and once at rate=1600 (p99=22.04ms, 0% errors) — clean pass, likely reaching parity with the other five stacks once run through the full dry-run methodology.
  - **Both Rust services now have distinct, real, understood, permanently-fixed root causes** — not workarounds: Rocket's was a Rust std/Hyper limitation (128 backlog, fixed via `LD_PRELOAD`), Actix-web's was an actix-web-specific keep-alive default (fixed via one config line). Neither was the same bug wearing two faces, despite both stacks showing similar-looking "capped throughput" symptoms initially.

- **Aug 18, 2026 (later) — a third, unrelated bug found underneath the keep-alive fix: container file descriptor exhaustion.** Re-running Actix-web at rate=1600 after the keep-alive fix still didn't cleanly reach parity — achieved only 581 req/s with `dropped_iterations` non-zero and elevated latency, and Jean explicitly pushed back on accepting this as "normal variance" ("I'm pretty sure there's still something wrong, there's no reason Actix doesn't make it when Rocket does. Analyse the different logs, k6 summaries, database logs, package transmissions, etc..."). Checked `pg_stat_activity` (no unusual load reaching Postgres) and `docker stats` (container sitting near-idle CPU, not busy) — ruled out both a database bottleneck and a CPU bottleneck, which pointed at something capacity-related instead. The decisive tell: k6 needed a wildly disproportionate number of concurrent VUs to sustain even the degraded throughput given the observed 1-2ms per-request latency — a Little's Law mismatch consistent with connections stuck waiting on a resource, not on the network or the database.
  - **Root cause**: `docker exec <container> sh -c 'ulimit -n'` showed 1024 — Docker's default per-container file descriptor limit, unrelated to language/framework, generic to any container regardless of what's running inside it.
  - **Fixed**: added `ulimits: { nofile: { soft: 65536, hard: 65536 } }` to *every* service in `docker-compose.yml`, not just Actix-web — this is a Docker default with no reason to single out one stack, the same fairness logic later applied to the backlog/keep-alive treatment. Verified at rate=1600: went from 581 req/s achieved (with dropped iterations) to 1599.76/1600 achieved, needing only 12 VUs — confirming the fix and quantifying just how much of a limiter the default 1024 had been.
  - Captured this bug and the two Rust ones together in a new user-level Claude Code skill, `backend-concurrency-defaults` (`~/.claude/skills/`), covering symptom signatures, known-bad defaults per stack, and fixes for all three — relevant to any future project on these same stacks, not just this one.

- **Aug 18, 2026 (later) — fairness pass: matched backlog/keep-alive fixes across the four remaining stacks, so the scrutiny already given to Rocket/Actix-web isn't lopsided.** Jean's framing: having optimized the two Rust stacks to handle much higher load, leaving Spring/Node/Bun at their unexamined defaults would bias the comparison in Rust's favor for reasons that have nothing to do with the hypothesis. Captured the generalized versions of both bug classes in a new user-level Claude Code skill (`backend-concurrency-defaults`) before applying them here, since they're relevant to any project on these stacks, not just this one.
  - **Spring Java/Kotlin** (`application.properties`, both identical): added `server.tomcat.accept-count=4096` (Tomcat's default `acceptCount` is ~100 — smaller than the Rust bug this project spent two days fixing) and `server.tomcat.keep-alive-timeout=75000` (falls back to `connectionTimeout`'s 20s otherwise).
  - **Node-hono** (`src/index.js`): `@hono/node-server`'s `serve()` doesn't expose backlog or keep-alive directly, but does accept an `options.createServer` override.   - **Bun-hono** (`src/index.js`): set `idleTimeout: 75` (Bun.serve()'s actual keep-alive knob, default 10s) for parity on that half. **Backlog could not be matched** — checked Bun's own `bun-types/serve.d.ts` directly and confirmed Bun.serve() has no public backlog option at all (unlike Node's `http.Server`).   - All four rebuilt (amd64), pushed to the registry, redeployed on the target VM, and verified individually: `nsenter`-confirmed backlog values (spring-java 4096, spring-kotlin 4096, node-hono 4096, bun-hono 512-unchanged/documented), `ulimit -n` 65536 on all four, and a functional `GET /items` returning 200 on each.
  - **Shell gotcha recurred once more, caught before it caused damage**: a `for stack in ...; do docker buildx build -t rg.fr-par.scw.cloud/slashbench/$stack:latest ...` loop (zsh) mangled `$stack:latest` into e.g. `spring-javaatest:latest` — zsh's bare `$var:modifier` filename-modifier syntax (`:l`, `:t`, `:e`, ... applied letter-by-letter to "latest") firing on an unbraced variable, the exact same failure mode logged earlier in this project. - **Aug 19, 2026 (later) — confirmed the 2400-vs-2000 dry-run ceilings are genuine CPU-driven differences, not leftover misconfiguration.** Jean asked directly for verification before committing to the official runs, given how many real bugs (backlog, keep-alive, ulimit) had already masqueraded as "just how this stack performs." Ran a live diagnostic per stack (fresh reseed, ~20s k6 burst at the rate one rung above its dry-run ceiling, `docker stats` sampled every 2s on the target, one `pg_stat_activity` snapshot at the end) rather than reaching for a new observability stack — Jean's call: the report's existing per-second cgroup sampling is enough, no need for OTel/Grafana just to answer a one-off root-cause question.
  - **Every stack's failure is 0% error rate with p99 blowing past the SLA** — no drops, no timeouts, no connection resets. That alone rules out a regression in the three already-fixed bug classes (all three announce themselves via non-zero error rates or connection failures, not smooth latency growth). `pg_stat_activity` showed exactly 20 idle connections for every stack at the snapshot moment — the pool is fully open and behaves identically everywhere, ruling out pool-size asymmetry too.
  - **The real mechanism: combined host CPU (app container + Postgres, both on `slashbench-target`) converges to ~360-400% — the full 4-vCPU ceiling — for every single stack** at its failing rate. Postgres alone consumes 275-370% of that in every case, since it's answering the same queries regardless of caller. What differs is how much of the *remaining* CPU each stack's own request handling burns: Rocket/Actix-web ~20-30% (leaves Postgres almost the whole host), Node/Bun ~30-50%, Spring Java/Kotlin ~40-210% (spikes hardest early in the burst, consistent with JIT/GC pressure under sudden load, though the container's own 8s-old startup residue is a confound worth naming rather than ignoring). Less app-side CPU overhead → more left over for Postgres to actually do the work → a higher sustainable ceiling before latency collapses — directly explaining the 2400 (Rust) vs 2000 (everyone else) split.
  - **Conclusion: the ceilings are real, runtime-driven CPU-efficiency differences, not a misconfiguration artifact** — smaller than the original hypothesis's hoped-for gap because Postgres, not the app, is the dominant consumer of this fixed 4-vCPU host's CPU. Honest, defensible story for the talk, and a stronger one than an unexplained "Rust is N× faster" number would have been.

Strongly consistent with the hypothesis, but this is a short unconstrained burst, not the official §4 sweep-under-SLA minimum-viable-footprint methodology — treat as a leading indicator, not the report's real memory number.
